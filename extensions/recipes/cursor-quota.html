Cursor Quota Widget Recipe

Capability

Source Cursor quota windows from the local machine for a baby-menu widget, using only the access token Cursor already stores locally plus Cursor's own dashboard HTTP API.

Do not depend on any separate quota CLI or npm package. The only external tool this recipe uses is sqlite3, a standard macOS system binary (not a per-product install), used strictly read-only to pull one existing token out of Cursor's own local database. When no usable local token exists, the token is rejected, or the API cannot be parsed, return an unavailable or sign-in-required result - do not fabricate or fall back to mock data.

Scope: this recipe covers only how to obtain and normalize the data. How the widget presents it - layout, states, copy, refresh controls - is left to the implementer and is intentionally not specified here.

This recipe is self-contained. Do not require external source code, websites, or implementation guides to complete it.

Recommended Data Source Order

PrioritySourceUse WhenExpected Data
1 Local Cursor state database + Dashboard API Cursor has been signed in at least once on this Mac and the token it stored still works. Plan name, included/auto/API usage percentages, billing cycle end.
2 Cached last-good snapshot The Dashboard API times out or is briefly unreachable, and a previous successful snapshot exists. The same shape as source 1, marked stale: true.

There is no separate CLI fallback. A quota-axi-style tool installed only under a Node version manager is not on the menu-bar app's PATH and must not be depended on; read the local database and call the API directly instead.

Local Auth Details

Read credentials only from cursor-quota/server.ts, never from the renderer.

Database path (macOS, verified present on this machine): ~/Library/Application Support/Cursor/User/globalStorage/state.vscdb. This is a SQLite database Cursor itself writes to and may have open while the widget queries it, so always query it read-only.

Query it with the sqlite3 CLI in read-only mode and set a short busy timeout so Cursor holding the database open is treated as a transient local read failure instead of a sign-in failure:

sqlite3 -readonly -cmd ".timeout 1000" "<path-to-state.vscdb>" \
  "SELECT key, value FROM ItemTable WHERE key IN ('cursorAuth/accessToken', 'cursorAuth/cachedEmail', 'cursorAuth/stripeMembershipType');"

Verified live keys present in ItemTable on this machine include cursorAuth/accessToken, cursorAuth/cachedEmail, cursorAuth/cachedSignUpType, cursorAuth/refreshToken, and cursorAuth/stripeMembershipType. Query only cursorAuth/accessToken, cursorAuth/cachedEmail, and cursorAuth/stripeMembershipType; do not retrieve cursorAuth/refreshToken or any other unused secret. Each queried value is a plain string (the access token is a JWT), not JSON-wrapped. Read cursorAuth/accessToken for the bearer token, cursorAuth/cachedEmail for the account email, and cursorAuth/stripeMembershipType (e.g. "free") as a plan fallback if the API call below does not return a plan name.

sqlite3 discovery. Menu-bar apps can have a trimmed PATH that omits sqlite3 even though it exists on the system. Try, in order: the bare sqlite3 command; then /usr/bin/sqlite3 (present on every macOS install); then /opt/homebrew/bin/sqlite3 and /usr/local/bin/sqlite3 (Homebrew installs). Use the first one that runs successfully. If none run, return an unavailable result - do not tell the user to install a quota tool, since sqlite3 ships with macOS.

Token expiry. The access token is usually a JWT (three base64url segments separated by .). You may decode the middle segment to read its exp claim (seconds since epoch) for diagnostics, but do not treat a past exp as final sign-in-required and do not skip the network because of it. Do not fail if the token cannot be decoded as a JWT at all - fall through and let the Dashboard API's own 401/403 response be the source of truth for rejection.

If the database file is missing or no cursorAuth/accessToken value is returned, return Cursor sign-in required without calling the network. If the query fails because the database is locked or busy after the busy timeout, return the cached snapshot marked stale when one exists, otherwise return an unavailable result. Other unreadable database or sqlite errors are unavailable local read failures, not evidence that the user is signed out. Never log, echo, or return the access token, refresh token, or raw database contents in errors, logs, or the response sent to the renderer.

Dashboard API Details

Primary request (required):

POST https://api2.cursor.sh/aiserver.v1.DashboardService/GetCurrentPeriodUsage
Authorization: Bearer <access_token>
content-type: application/json
connect-protocol-version: 1

{}

Optional secondary request, for the plan name only (skip it entirely if the primary request already fails; do not let its failure affect the primary result):

POST https://api2.cursor.sh/aiserver.v1.DashboardService/GetPlanInfo
Authorization: Bearer <access_token>
content-type: application/json
connect-protocol-version: 1

{}

Use a hard timeout around 15 seconds per request. Treat 401 or 403 on the primary request as Cursor sign-in required. Any other non-2xx status, a timeout, or a network error on the primary request falls back to the cached snapshot when one exists, otherwise an unavailable result.

Live output is authoritative. Parse defensively: tolerate added fields, missing optional fields, and non-numeric percentages. Do not default a missing percent-used field to 0 - if it is not a finite number, omit that window instead. billingCycleStart/billingCycleEnd are epoch-millisecond values encoded as decimal strings; parse them with Number(...) before constructing a Date.

Field mapping:

  • planUsage.totalPercentUsed -> window id: "included_usage", label: "included usage", kind: "monthly".
  • planUsage.autoPercentUsed -> window id: "auto_usage", label: "auto usage", kind: "monthly".
  • planUsage.apiPercentUsed -> window id: "api_usage", label: "API usage", kind: "monthly".
  • billingCycleEnd -> resetAt on every window (converted from the epoch-ms string to an ISO date), when it parses.
  • planInfo.planName from the optional GetPlanInfo call, or else the sqlite cursorAuth/stripeMembershipType value capitalized, -> plan.

One axis, consistently. Percentages here are percent used from 0 to 100. Remaining is 100 - percentUsed. Whatever the widget chooses to show, the label, number, and any meter for a given window must all describe the same axis.

Normalized Snapshot Type

type CursorQuotaSnapshot = {
  source: "api";
  accountEmail?: string;
  plan?: string;
  windows: Array<{
    id: "included_usage" | "auto_usage" | "api_usage";
    label: string;
    kind?: "monthly";
    percentUsed: number;          // canonical, percent USED (0-100)
    percentRemaining?: number;    // optional, derive as 100 - percentUsed when absent
    resetAt?: string;
  }>;
  refreshedAt: string;
  stale: boolean;
  status?: string;
};

Clamp numeric percentages to the inclusive range 0..100.

Implementation Contract

All data acquisition lives in cursor-quota/server.ts: sqlite3 discovery and invocation, the HTTP requests, timeouts, and parsing. Expose it as a getQuota server action invoked from the renderer with window.babyMenu.capabilities.invoke("cursor-quota", "getQuota", input). Do not add preload methods, per-widget IPC channels, core renderer widgets, or WidgetHost registration; Baby Menu discovers extension widgets automatically.

The data is safe to refresh roughly every 5 minutes while the widget is visible. Use viewRefreshIntervalMs or refreshView for visible refresh. Do not add a background task unless the user explicitly asks for quota monitoring while the popover is closed.

Before writing the parser, inspect the real state.vscdb keys and the real Dashboard API responses on this machine to confirm the current shapes; do not guess or pattern-complete a field name. Before reporting the work done, invoke getQuota (or an equivalent one-off check) against the real source and confirm the exact windows and values you expect actually come back - reasoning through the shapes on paper is not enough.

Server action response shape:

type QuotaResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: string; sourceTried: string[] };

Error and Unavailable Handling

These are data outcomes the server action returns, not UI copy.

  • If sqlite3 cannot be located under any of the fallback paths, return an unavailable error (Cursor quota unavailable) with sourceTried: ["local-db"].
  • If the database is missing or has no cursorAuth/accessToken value, return Cursor sign-in required without calling the network.
  • If the database query fails because the database is locked or busy, return the previous successful snapshot marked stale: true when one exists; otherwise return an unavailable error. Treat other sqlite read failures as unavailable local read failures, not sign-in-required.
  • If the Dashboard API returns 401 or 403, return Cursor sign-in required.
  • If the primary request times out or the network is briefly unreachable, return the previous successful snapshot marked stale: true when one exists; otherwise return an unavailable error.
  • If the optional GetPlanInfo call fails for any reason, omit plan (or use the sqlite fallback) rather than failing the whole result.
  • Ignore reset timestamps that fail to parse as dates. Keep the quota percentage and omit resetAt instead of showing a misleading date.
  • Never log, echo, or return the access token, refresh token, or database contents in errors or logs.

Security Constraints

  • Credential, filesystem, shell, and network access belongs only in extension-owned server actions behind window.babyMenu.capabilities.invoke.
  • Never commit secrets, token dumps, local database contents, or captured command output that might include credentials.
  • Do not send Cursor credentials to the renderer. The renderer receives only the normalized snapshot.
  • Keep sqlite3 stderr out of user-visible errors unless it has been scrubbed for token-like values.

Acceptance Criteria

  • The extension reads the access token from Cursor's own state.vscdb via read-only sqlite3 and calls the Dashboard API directly from cursor-quota/server.ts. It never execs or requires quota-axi or any other separate quota CLI.
  • sqlite3 is located via a PATH lookup plus full-path fallbacks rather than assumed to be on PATH.
  • The snapshot includes Cursor plan (when discoverable), refreshed time, stale state, and all three usage windows from live output.
  • percentUsed is treated as used, not remaining, and any label or meter uses one axis consistently.
  • Missing token, rejected token, invalid API responses, and timeouts produce explicit unavailable, sign-in-required, or stale results without mock data.
  • No token, cookie, local database, or credential value is logged, returned, committed, or exposed to the renderer.
  • The implementer verifies the finished server action against the real local database and the real Dashboard API on this machine before reporting done.
