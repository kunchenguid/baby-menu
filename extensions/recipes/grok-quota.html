Grok Quota Widget Recipe

Capability

Source Grok quota and credit windows from the local machine for a baby-menu widget, using only Grok's own local auth file and its billing HTTP API.

Do not depend on any separate CLI or npm package to read quota. Users must not be asked to install anything beyond having signed in to Grok once. Read the local Grok credential file directly and call the billing API with it. When no usable local credential exists, every credential is rejected by the live API, or the API cannot be parsed, return an unavailable or sign-in-required result - do not fabricate or fall back to mock data.

Scope: this recipe covers only how to obtain and normalize the data. How the widget presents it - layout, states, copy, refresh controls - is left to the implementer and is intentionally not specified here.

This recipe is self-contained. Do not require external source code, websites, or implementation guides to complete it.

Recommended Data Source Order

PrioritySourceUse WhenExpected Data
1 Local Grok auth file + billing API A usable local Grok credential exists and the billing API responds. Credit usage percent, product-scoped usage (e.g. GrokBuild), billing period end, prepaid balance.
2 Cached last-good snapshot The billing API times out, rate-limits, or is briefly unreachable, and a previous successful snapshot exists. The same shape as source 1, marked stale: true.

There is no CLI fallback for Grok in this recipe. A separate quota-axi-style tool is only ever installed under a Node version manager, which is not on the menu-bar app's PATH; shelling out to it fails silently for most users. Read the auth file and call the API directly instead.

Local Auth Details

Read credentials only from grok-quota/server.ts, never from the renderer.

Resolve the auth file path in this order:

  1. $GROK_AUTH_JSON - if set, treat its value as inline JSON (the same shape as the file below) instead of reading a file at all.
  2. $GROK_AUTH_PATH - if set, treat its value as an explicit path to the auth file.
  3. $GROK_HOME/auth.json - if GROK_HOME is set.
  4. ~/.grok/auth.json - default location, verified present on this machine.

The file is a JSON object keyed by an auth-scope identifier (a URL-like string such as an OIDC issuer plus client id, or a sign-in URL). Each value is an object that may include:

{
  "<scope-key>": {
    "key": "<bearer-token>",
    "auth_mode": "oidc",
    "email": "user@example.com",
    "expires_at": "2026-07-09T18:48:56.527168Z",
    "refresh_token": "..."
  }
}

Verified live on this machine: the key observed was of the form https://auth.x.ai::<oidc-client-id> with fields key, auth_mode, email, expires_at, and refresh_token present. Do not assume this exact key format; iterate every entry in the object rather than looking up one hardcoded key.

Candidate selection. Collect every entry that has a non-empty string key field - that field is the bearer token to send to the billing API. Classify each candidate as a "session" credential if it carries refresh_token and/or auth_mode, versus a raw API-key-shaped entry that carries neither. Prefer session credentials over API-key-shaped ones. Within the same class, use expires_at only as an ordering hint: prefer an entry whose timestamp is present, parseable, and in the future over one whose timestamp has already passed, then entries with no parseable timestamp. Do not discard or skip a candidate solely because expires_at has passed. Try every candidate with a usable key in order and let the billing API's own 401/403 response be the source of truth for rejection. If an auth source is successfully read and parsed but has no usable key anywhere, return Grok sign-in required without calling the network. If the auth source cannot be read or parsed, follow the cached-stale-or-unavailable path instead of reporting sign-in required.

Optional client version header value: read ~/.grok/version.json ({ "version": "0.2.93", ... }) and use its version field for x-grok-client-version below. If that file is missing or unparseable, omit the header entirely rather than guessing a version.

Never log, echo, or return the bearer token, refresh token, or raw auth file contents in errors, logs, or the response sent to the renderer.

Billing API Details

Request:

GET https://cli-chat-proxy.grok.com/v1/billing?format=credits
Authorization: Bearer <key>
Accept: application/json
x-grok-client-version: <version>   (optional, omit if unknown)

Use a hard timeout around 15 seconds. Treat the response status as follows: 401 or 403 for one candidate means that candidate was rejected, so try the next usable credential candidate before reporting sign-in required; only return Grok sign-in required after every usable candidate has been rejected. 429 means rate-limited - return the cached snapshot marked stale if one exists, otherwise an unavailable result noting the rate limit. Any other non-2xx status, network error, or timeout falls back to the cached snapshot when one exists, otherwise an unavailable result.

Verified live response shape from this exact endpoint on this machine on 2026-07-09 (values shown are this account's real values at capture time, not samples):

{
  "config": {
    "currentPeriod": {
      "type": "USAGE_PERIOD_TYPE_WEEKLY",
      "start": "2026-07-06T19:59:29.885889+00:00",
      "end": "2026-07-13T19:59:29.885889+00:00"
    },
    "creditUsagePercent": 49.0,
    "onDemandCap": { "val": 0 },
    "onDemandUsed": { "val": 0 },
    "productUsage": [
      { "product": "GrokBuild", "usagePercent": 49.0 }
    ],
    "isUnifiedBillingUser": true,
    "prepaidBalance": { "val": 0 },
    "topUpMethod": "TOP_UP_METHOD_SAVED_PAYMENT_METHOD",
    "billingPeriodStart": "2026-07-06T19:59:29.885889+00:00",
    "billingPeriodEnd": "2026-07-13T19:59:29.885889+00:00"
  }
}

Live output is authoritative. Parse defensively: tolerate added fields, missing optional fields, missing productUsage entries, and non-numeric percentages. Do not default a missing creditUsagePercent to 0 - if it is not a finite number, omit the credits window instead. All fields live under a top-level config object; there is no other wrapper.

Field mapping:

  • config.creditUsagePercent -> the global credits window, kind: "credits", percentUsed clamped to 0..100.
  • config.productUsage[] -> one window per entry with id: "product:" + slug(product) where slug lowercases the product name and strips anything that is not a-z0-9 (e.g. "GrokBuild" -> product:grokbuild). Preserve the exact product name as label. usagePercent maps to percentUsed.
  • config.billingPeriodEnd (fall back to config.currentPeriod.end when absent) -> resetAt on every window, when it parses as a valid date.
  • config.prepaidBalance.val -> credits.remaining when it is a finite number; credits.unit is "credits".
  • config.subscription_tier or similarly named plan field, if present -> plan. This account's live response had no such field; treat it as optional and omit plan when absent.

One axis, consistently. percentUsed is percent used from 0 to 100. Remaining is 100 - percentUsed. Whatever the widget chooses to show, the label, number, and any meter for a given window must all describe the same axis.

Normalized Snapshot Type

type GrokQuotaSnapshot = {
  source: "api";
  plan?: string;
  windows: Array<{
    id: "credits" | `product:${string}`;
    label: string;
    kind?: "credits";
    percentUsed: number;          // canonical, percent USED (0-100)
    percentRemaining?: number;    // optional, derive as 100 - percentUsed when absent
    resetAt?: string;
  }>;
  credits?: {
    remaining?: number;
    unit?: string;
  };
  refreshedAt: string;
  stale: boolean;
  status?: string;                // e.g. "rate-limited" when serving cache after a 429
};

Clamp numeric percentages to the inclusive range 0..100. Preserve every product-scoped window from productUsage rather than dropping unfamiliar product names, since Grok may add products later.

Implementation Contract

All data acquisition lives in grok-quota/server.ts: auth file resolution, the HTTP request, timeouts, and parsing. Expose it as a getQuota server action invoked from the renderer with window.babyMenu.capabilities.invoke("grok-quota", "getQuota", input). Do not add preload methods, per-widget IPC channels, core renderer widgets, or WidgetHost registration; Baby Menu discovers extension widgets automatically.

The data is safe to refresh roughly every 5 minutes while the widget is visible. Use viewRefreshIntervalMs or refreshView for visible refresh. Do not add a background task unless the user explicitly asks for quota monitoring while the popover is closed.

Before writing the parser, inspect the real ~/.grok/auth.json file and the real billing API response on this machine to confirm the current auth shape and response fields; do not guess or pattern-complete a field name. Before reporting the work done, invoke getQuota (or an equivalent one-off check) against the real source and confirm the exact windows and values you expect actually come back for the live, unavailable, and stale states - reasoning through the shapes on paper is not enough.

Server action response shape:

type QuotaResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: string; sourceTried: string[] };

Error and Unavailable Handling

These are data outcomes the server action returns, not UI copy.

  • If the auth source is missing, unreadable, malformed, or local auth parsing fails before a credential candidate can be built, return the previous successful snapshot marked stale: true when one exists; otherwise return an unavailable error (Grok quota unavailable) with sourceTried: ["local-auth"].
  • If an auth source is successfully read and parsed but no entry has a usable non-empty key, return Grok sign-in required with sourceTried: ["local-auth"] without calling the network.
  • If the billing API returns 401 or 403 for one credential candidate, try the next usable candidate. Return Grok sign-in required only after every usable candidate is rejected.
  • If the billing API returns 429, returns another non-auth non-2xx status such as 5xx, times out, or the network is briefly unreachable, return the previous successful snapshot marked stale: true when one exists; otherwise return an unavailable error (Grok quota unavailable).
  • If the response cannot be parsed into a usable credits or product window, return an unavailable error rather than guessing.
  • Ignore reset timestamps that fail to parse as dates. Keep the quota percentage and omit resetAt instead of showing a misleading date.
  • Never log, echo, or return the bearer token, refresh token, or auth file contents in errors or logs.

Security Constraints

  • Credential, filesystem, and network access belongs only in extension-owned server actions behind window.babyMenu.capabilities.invoke.
  • Never commit secrets, token dumps, local auth file contents, or captured command output that might include credentials.
  • Do not send Grok credentials to the renderer. The renderer receives only the normalized snapshot.

Acceptance Criteria

  • The extension reads the local Grok auth file (or its env overrides) and calls the billing API directly from grok-quota/server.ts. It never execs or requires quota-axi or any other separate quota CLI.
  • Candidate credential selection prefers session-shaped entries over API-key-shaped ones, uses expires_at only for ordering, and tries the next candidate when one credential is rejected.
  • The snapshot includes refreshed time, stale state, top-level credits when present, and all usable windows from live output, including product-scoped ids like product:grokbuild.
  • percentUsed is treated as used, not remaining, and any label or meter uses one axis consistently.
  • Missing auth, rejected auth, invalid API responses, and timeouts produce explicit unavailable, sign-in-required, or stale results without mock data.
  • No token, cookie, or credential value is logged, returned, committed, or exposed to the renderer.
  • The implementer verifies the finished server action against the real local auth file and the real billing API on this machine before reporting done.
