GitHub Copilot Quota Widget Recipe

Capability

Source GitHub Copilot quota windows from the local machine for a baby-menu widget, using only a Copilot-issued OAuth token already stored locally by any Copilot-enabled editor/tool plus GitHub's own Copilot internal API.

Do not depend on any separate quota CLI or npm package. When no usable local token exists, the token is rejected, or the API cannot be parsed, return an unavailable or sign-in-required result - do not fabricate or fall back to mock data.

Scope: this recipe covers only how to obtain and normalize the data. How the widget presents it - layout, states, copy, refresh controls - is left to the implementer and is intentionally not specified here.

This recipe is self-contained. Do not require external source code, websites, or implementation guides to complete it.

Recommended Data Source Order

PrioritySourceUse WhenExpected Data
1 Local Copilot apps.json + copilot_internal/user API Any Copilot-enabled tool (editor extension, CLI, Neovim plugin, etc.) has signed in on this machine and its stored token still works. Login, plan, per-window quota (chat, completions, premium interactions), quota reset date.
2 Cached last-good snapshot The API times out or is briefly unreachable, and a previous successful snapshot exists. The same shape as source 1, marked stale: true.

There is no separate CLI fallback. A quota-axi-style tool installed only under a Node version manager is not on the menu-bar app's PATH and must not be depended on; read the local token and call the API directly instead.

Local Auth Details

Read credentials only from copilot-quota/server.ts, never from the renderer.

Check both of these paths and read every file that exists and parses as JSON:

  1. ~/.config/github-copilot/apps.json - verified present on this machine.
  2. ~/Library/Application Support/github-copilot/apps.json - some macOS-native Copilot clients use this path instead; not present on this machine, but check it before giving up.

The file is a JSON object keyed by an opaque app-registration identifier (commonly of the form <host>:<github-app-id>:<client-name>, e.g. github.com:Iv1.b507a08c87ecfe98:Neovim as verified on this machine). Each value has this shape:

{
  "<app-key>": {
    "user": "<github-login>",
    "oauth_token": "ghu_...",
    "githubAppId": "Iv1...."
  }
}

Candidate selection. Collect every entry from every readable apps.json file with a non-empty string oauth_token. Prefer entries whose key starts with github.com (tokens scoped to github.com, which is what the API below expects) over any other host. Within the same host preference, prefer candidates from the most recently modified file, then keep file order and object iteration order stable as tie-breakers. Try candidates in that order. If no token candidates can be built and any existing apps.json file was unreadable or malformed, follow the cached-stale-or-unavailable path instead of reporting sign-in required. Return Copilot sign-in required without calling the network only when at least one existing apps.json file parses successfully, no existing apps.json file failed read or parse, and no parsed entry has a usable oauth_token.

Note that the account identity comes back from the API response's own login field, not from the file's user field - the file may be labeled with an unrelated client name (e.g. a Neovim plugin's registration key) while still authenticating as the correct GitHub account. Do not assume the app-key's trailing segment names the product actually in use.

Never log, echo, or return the OAuth token or raw apps.json contents in errors, logs, or the response sent to the renderer.

Copilot Internal API Details

Request:

GET https://api.github.com/copilot_internal/user
Authorization: Bearer <oauth_token>
Accept: application/json
User-Agent: GitHubCopilotChat/1.0

The exact User-Agent string is not load-bearing for authorization, but GitHub's API rejects requests with no User-Agent at all; send a stable, descriptive value like the one above. Use a hard timeout around 15 seconds. For 403, first check for rate limits or transient policy blocks. Do not classify every 403 as rejected auth: when the response has x-ratelimit-remaining: 0, a retry-after header, or a body message mentioning rate limits, secondary rate limits, abuse detection, or a transient GitHub policy block, return the cached snapshot when one exists, otherwise an unavailable result. Use x-ratelimit-reset only when x-ratelimit-remaining is 0 to decide when the current primary-limit window resets; do not let that header by itself classify a 403 as rate-limited. Treat 401, or any remaining non-transient 403, as that token candidate being rejected, then try the next token candidate before reporting sign-in required; only return Copilot sign-in required after every usable token candidate has been rejected. Any other non-2xx status, a timeout, or a network error follows the same cached-stale-or-unavailable path.

Reset timestamp rule (important). Every quota_snapshots.<window>.quota_reset_at value observed on this machine was the literal number 0 - an epoch-zero placeholder, not a real reset time. Never render a Date built from quota_reset_at when it is 0 or otherwise resolves to the 1970 epoch. Use the top-level quota_reset_date_utc as the shared reset time for every window instead; it carries the real monthly reset date (e.g. the 1st of next month).

Live output is authoritative. Parse defensively: tolerate added fields, missing optional fields, missing windows, and non-numeric percentages. Do not default a missing percent_remaining to 0 or 100 - if it is not a finite number, omit that window instead.

Field mapping:

  • quota_snapshots.chat -> window id: "chat", label: "chat", kind: "monthly".
  • quota_snapshots.completions -> window id: "completions", label: "completions", kind: "monthly".
  • quota_snapshots.premium_interactions -> window id: "premium_interactions", label: "premium interactions", kind: "monthly".
  • Any other quota_snapshots.<window> entry with a finite percent_remaining -> window id equal to that snapshot key, label equal to the key with underscores replaced by spaces, kind: "monthly".
  • Each window's percentRemaining comes directly from percent_remaining; derive percentUsed = 100 - percentRemaining. When unlimited is true, still report the API's own percent_remaining (typically 100) rather than fabricating a different number.
  • resetAt for every window -> the top-level quota_reset_date_utc when it parses as a valid date; never the per-window quota_reset_at.
  • copilot_plan -> plan. login -> accountLogin.

One axis, consistently. Percentages here can be sourced as percent remaining directly from the API; still ensure the label, number, and any meter for a given window all describe the same axis (used vs. remaining) once normalized into percentUsed.

Normalized Snapshot Type

type CopilotQuotaSnapshot = {
  source: "api";
  accountLogin?: string;
  plan?: string;
  windows: Array<{
    id: "chat" | "completions" | "premium_interactions" | (string & {});
    label: string;
    kind?: "monthly";
    percentUsed: number;          // canonical, percent USED (0-100)
    percentRemaining?: number;    // optional, derive as 100 - percentUsed when absent
    resetAt?: string;             // from quota_reset_date_utc; never epoch-zero
  }>;
  refreshedAt: string;
  stale: boolean;
  status?: string;
};

Clamp numeric percentages to the inclusive range 0..100. Preserve unknown windows in quota_snapshots rather than dropping them, since GitHub may add new Copilot quota categories later.

Implementation Contract

All data acquisition lives in copilot-quota/server.ts: apps.json discovery, the HTTP request, timeouts, and parsing. Expose it as a getQuota server action invoked from the renderer with window.babyMenu.capabilities.invoke("copilot-quota", "getQuota", input). Do not add preload methods, per-widget IPC channels, core renderer widgets, or WidgetHost registration; Baby Menu discovers extension widgets automatically.

The data is safe to refresh roughly every 5 minutes while the widget is visible. Use viewRefreshIntervalMs or refreshView for visible refresh. Do not add a background task unless the user explicitly asks for quota monitoring while the popover is closed.

Before writing the parser, inspect the real apps.json file and the real API response on this machine to confirm the current shapes; do not guess or pattern-complete a field name. Before reporting the work done, invoke getQuota (or an equivalent one-off check) against the real source and confirm the exact windows and values you expect actually come back, including that epoch-zero reset dates are suppressed - reasoning through the shapes on paper is not enough.

Server action response shape:

type QuotaResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: string; sourceTried: string[] };

Error and Unavailable Handling

These are data outcomes the server action returns, not UI copy.

  • If neither apps.json path exists, every existing local auth file is unreadable or malformed, any existing local auth file is unreadable or malformed while no token candidates can be built from the remaining parsed files, or local auth parsing fails before a token candidate can be built, return the previous successful snapshot marked stale: true when one exists; otherwise return an unavailable error (Copilot quota unavailable) with sourceTried: ["local-auth"].
  • If at least one existing apps.json file parses successfully, no existing apps.json file failed read or parse, and no parsed entry has a usable oauth_token, return Copilot sign-in required with sourceTried: ["local-auth"] without calling the network.
  • If the API returns 401, or a non-transient 403 after the rate-limit and policy-block checks below, try the next usable token. Return Copilot sign-in required only after every usable token candidate is rejected.
  • If the API returns a rate-limited or transient-policy 403 (for example x-ratelimit-remaining: 0, retry-after, or a body mentioning rate limits, secondary rate limits, abuse detection, or a transient GitHub policy block), times out, or the network is briefly unreachable, return the previous successful snapshot marked stale: true when one exists; otherwise return an unavailable error (Copilot quota unavailable). Use x-ratelimit-reset as the retry time only with x-ratelimit-remaining: 0.
  • If quota_snapshots is missing or has no usable window, return an unavailable error rather than guessing.
  • Never render an epoch-zero or otherwise unparseable reset timestamp; omit resetAt instead of showing 1970.
  • Never log, echo, or return the OAuth token or apps.json contents in errors or logs.

Security Constraints

  • Credential, filesystem, and network access belongs only in extension-owned server actions behind window.babyMenu.capabilities.invoke.
  • Never commit secrets, token dumps, local apps.json contents, or captured command output that might include credentials.
  • Do not send the Copilot OAuth token to the renderer. The renderer receives only the normalized snapshot.

Acceptance Criteria

  • The extension reads an oauth_token from a local apps.json file and calls copilot_internal/user directly from copilot-quota/server.ts. It never execs or requires quota-axi or any other separate quota CLI.
  • Both known apps.json paths are checked, token candidates are collected from every readable file, and github.com-scoped token entries are preferred.
  • The snapshot includes Copilot plan, account login, refreshed time, stale state, and all usable windows from quota_snapshots.
  • percentUsed is treated as used, not remaining, and any label or meter uses one axis consistently.
  • Epoch-zero or otherwise non-useful per-window reset timestamps are never rendered; the top-level monthly reset date is used instead.
  • Malformed or unreadable apps.json files produce stale or unavailable results, not sign-in-required. Parsed auth files with no usable token, rejected token candidates, invalid API responses, and timeouts produce explicit unavailable, sign-in-required, or stale results without mock data.
  • No token, cookie, apps.json content, or credential value is logged, returned, committed, or exposed to the renderer.
  • The implementer verifies the finished server action against the real local apps.json and the real API on this machine before reporting done.
