Codex Quota Widget Recipe

Capability

Source Codex usage limits, credits, and reset windows from local Codex credentials or CLI state for a baby-menu widget.

Use real local data only. When no usable local source is available, return an unavailable or sign-in-required result - do not fabricate or fall back to mock data.

Scope: this recipe covers only how to obtain and normalize the data. How the widget presents it - layout, states, copy, refresh controls - is left to the implementer and is intentionally not specified here.

This recipe is self-contained. Do not require external source code, websites, or implementation guides to complete it.

Recommended Data Source Order

PrioritySourceUse WhenExpected Data
1 Codex OAuth usage API ~/.codex/auth.json or $CODEX_HOME/auth.json contains usable OAuth credentials. Rate limit windows, reset timestamps, account identity, plan hints, credit snapshot when available.
2 Codex CLI RPC app server The codex CLI is installed and signed in. Rate limit windows, credits, account identity.

OAuth Usage API Details

Credential locations to check from codex-quota/server.ts only:

  • $CODEX_HOME/auth.json if CODEX_HOME is set.
  • ~/.codex/auth.json otherwise.

Unlike Claude, Codex stores credentials in a plain file, not the macOS Keychain, so a file read is sufficient. Do not read the Keychain for Codex.

Parse auth.json with this precedence:

  1. If a non-empty top-level OPENAI_API_KEY string is present, use it directly as the bearer token (API-key auth).
  2. Otherwise read the tokens object: access_token (or accessToken), refresh_token (or refreshToken), and optionally id_token / account_id. Accept both snake_case and camelCase keys.
{
  "OPENAI_API_KEY": null,                 // when set, use as the bearer token directly
  "tokens": {
    "access_token": "...",
    "refresh_token": "...",
    "id_token": "...",                    // optional
    "account_id": "..."                   // optional
  },
  "last_refresh": "2026-05-22T08:21:00Z"  // used for the staleness check below
}

If tokens is missing or has no access_token, treat it as a sign-in-required error (Run `codex` to log in.) rather than failing silently. Never log or echo the token values, and read credentials only inside the server action, never in the renderer.

Request:

GET https://chatgpt.com/backend-api/wham/usage
Authorization: Bearer <access_token>
ChatGPT-Account-Id: <tokens.account_id>

Send the ChatGPT-Account-Id header from tokens.account_id (or the account id decoded from the JWT) - the usage call needs it.

Response shape - parse these fields, but treat the live response as canonical. Usage lives under rate_limit, and each window carries used_percent (percent used, 0-100), so remaining = 100 - used_percent. primary_window is the short session window (its limit_window_seconds is ~18000 = 5h) and secondary_window is the weekly window (~604800 = 7d). reset_at is epoch seconds (multiply by 1000 for a JS Date); reset_after_seconds is the countdown.

The live API is the source of truth. This shape was captured from the real endpoint at the time of writing; the remote API can change field names, nesting, units, or window keys without notice. Confirm the fields against the actual response you receive (and via web search for the current API) before depending on them, and parse defensively - tolerate missing, added, renamed, or null fields and never assume a field is present. If the response no longer matches anything you can parse, return an unavailable or sign-in-required result rather than showing a wrong or fabricated number.

{
  "email": "you@example.com",
  "plan_type": "pro",
  "rate_limit": {
    "allowed": true, "limit_reached": false,
    "primary_window":   { "used_percent": 25, "limit_window_seconds": 18000,  "reset_at": 1780007894 },
    "secondary_window": { "used_percent": 70, "limit_window_seconds": 604800, "reset_at": 1780176266 }
  },
  "credits": { "has_credits": false, "unlimited": false, "balance": "0" }
}

So for the example above the session window is 25% used (equivalently 75% remaining) and the weekly window is 70% used (30% remaining). Map primary_window to the session/5-hour window and secondary_window to the weekly window; map email to accountEmail, plan_type to plan, and credits through. Do not default a missing used_percent to 0 (that hides the real number); omit a window that has no numeric used_percent instead.

One axis, consistently. "Used" and "remaining" are the same number from opposite ends (remaining = 100 - used). Whatever you choose to present, the label, the number, and any progress/meter for a given window must all describe the same axis. A meter or number labeled "left"/"remaining" must carry the remaining value, not the used value (a 25%-used window is "75% left", and a "left" meter should read three-quarters full). This is a correctness constraint only - it does not require a meter, a number, or any particular label or layout.

If the token metadata includes a refresh timestamp and it is older than roughly 8 days, prefer returning a sign-in or refresh-needed error for the first implementation rather than silently using a stale token.

Normalize response data into this shape:

type CodexQuotaSnapshot = {
  source: "oauth" | "cli-rpc";
  accountEmail?: string;
  plan?: string;
  windows: Array<{
    id: "five_hour" | "weekly" | "primary" | "secondary";
    label: string;
    percentUsed?: number;        // canonical, percent USED (0-100); derive remaining as 100 - percentUsed
    resetText?: string;
    resetAt?: string;
  }>;
  credits?: {
    balance?: number;
    hasCredits?: boolean;
    unlimited?: boolean;
  };
  refreshedAt: string;
  stale: boolean;
};

Codex CLI RPC Details

Run privileged CLI work in codex-quota/server.ts behind window.babyMenu.capabilities.invoke. Do not expose Node APIs to the renderer.

Command:

codex -s read-only -a untrusted app-server

JSON-RPC flow over stdin/stdout:

  1. Send initialize with a simple client name and version.
  2. Send account/read to get account identity when available.
  3. Send account/rateLimits/read to get windows and credits.
  4. Terminate the child process after the request.

Timeouts:

  • Allow up to 15 seconds for app-server startup and initialize.
  • Allow up to 8 seconds per normal RPC method.
  • Kill the child process on timeout so future refreshes are not blocked.

Expected data:

  • Usage windows may arrive as primary/secondary or five-hour/weekly equivalents.
  • Credit data may include balance, hasCredits, and unlimited flags.
  • Account identity may include email and plan type.

Implementation Contract

All data acquisition lives in codex-quota/server.ts: token reads, the CLI RPC, network calls, timeouts, and parsing. Expose it as a getQuota server action invoked from the renderer with window.babyMenu.capabilities.invoke("codex-quota", "getQuota", input). Do not add preload methods, per-widget IPC channels, core renderer widgets, or WidgetHost registration; Baby Menu discovers extension widgets automatically.

The data is safe to refresh roughly every 5 minutes; how and when the widget triggers a refresh is the widget's concern, not this recipe's.

Do not add test or documentation files for the extension. Verify by reasoning through the parser paths, the server action response shape, and the widget's rendered unavailable, stale, and live states.

Server action response shape:

type QuotaResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: string; sourceTried: string[] };

Error Handling

These are data outcomes the server action returns, not UI copy.

  • If no auth file or CLI is available, return an unavailable error (Codex quota unavailable). Do not return mock data.
  • If the CLI app-server times out, return the previous successful snapshot marked stale: true when one exists.
  • If credentials are expired, return a Codex sign-in required error rather than silently using a stale token.
  • If macOS blocks the CLI executable, return a Codex CLI could not be launched error.
  • Never log, echo, or return token or cookie values in errors or logs.
