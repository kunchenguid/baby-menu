Claude Code Quota Widget Recipe

Capability

Source Claude Code usage limits from the local machine for a baby-menu widget.

Use real local Claude credentials and CLI output only. When no usable local source is available, return an unavailable or sign-in-required result - do not fabricate or fall back to mock data.

Scope: this recipe covers only how to obtain and normalize the data. How the widget presents it - layout, states, copy, refresh controls - is left to the implementer and is intentionally not specified here.

This recipe is self-contained. Do not require external source code, websites, or implementation guides to complete it.

Recommended Data Source Order

PrioritySourceUse WhenExpected Data
1 Claude OAuth usage API A usable OAuth access token exists. Five-hour, seven-day, Sonnet weekly, Opus weekly, extra usage spend, plan hints.
2 Claude CLI /usage probe OAuth is unavailable but the claude CLI is installed and signed in. Current session percentage, current week percentage, reset text, account and org lines when present.

OAuth Usage API Details

Credential locations to check from claude-code-quota/server.ts only, in this fallback order:

  1. ~/.claude/.credentials.json - present on Linux and any setup where Claude Code wrote a file-based credential.
  2. macOS login Keychain - a generic-password item with service name Claude Code-credentials. This is where the Claude Code CLI stores its OAuth credentials on macOS, so on a typical Mac the file above does not exist and the Keychain is the real source. Do not skip it. Read it from the server action with the security CLI: security find-generic-password -s "Claude Code-credentials" -w, which prints the secret blob to stdout. Always check the file first, then fall back to this Keychain service.
  3. Future app-local credential cache under Electron user data, not committed to the repo.

The file and the Keychain blob hold the same JSON shape. Parse claudeAiOauth and read the access token from it:

{
  "claudeAiOauth": {
    "accessToken": "sk-ant-oat01-...",
    "refreshToken": "sk-ant-ort01-...",
    "expiresAt": 1780000000000,          // epoch ms; treat as expired / refresh-needed when in the past
    "scopes": ["user:inference", "user:profile"],
    "subscriptionType": "max"            // maps to the plan label: pro, max, ...
  }
}

Also accept accessToken / access_token at the JSON root as a fallback, since some writers store the token at the top level rather than under claudeAiOauth. Prefer a token whose scopes can call usage APIs; tokens with only inference scope may fail.

macOS Keychain notes: the first security find-generic-password read of an item owned by the claude CLI can trigger a one-time macOS permission prompt for Baby Menu; that is expected, and "Always Allow" authorizes future reads. Never log or echo the secret blob, the access token, or the refresh token, and read credentials only inside the server action, never in the renderer.

Request:

GET https://api.anthropic.com/api/oauth/usage
Authorization: Bearer <access_token>
anthropic-beta: oauth-2025-04-20

Response shape - parse these fields, but treat the live response as canonical. The body is a flat object keyed by window id, with no usage / data wrapper. Each present window is { utilization, resets_at } where utilization is the percent used (0-100), so remaining = 100 - utilization. A window key may be null (the user has no such window) - skip nulls, do not treat them as 0% used. resets_at is an ISO-8601 timestamp or null.

The live API is the source of truth. This shape was captured from the real endpoint at the time of writing; the remote API can change field names, nesting, units, or window keys without notice. Confirm the fields against the actual response you receive (and via web search for the current API) before depending on them, and parse defensively - tolerate missing, added, renamed, or null fields and never assume a field is present. If the response no longer matches anything you can parse, return an unavailable or sign-in-required result rather than showing a wrong or fabricated number.

{
  "five_hour":         { "utilization": 20.0, "resets_at": "2026-05-28T21:30:00Z" },
  "seven_day":         { "utilization": 4.0,  "resets_at": "2026-05-30T15:00:00Z" },
  "seven_day_opus":    null,
  "seven_day_sonnet":  { "utilization": 0.0,  "resets_at": null },
  "extra_usage":       { "is_enabled": false, "monthly_limit": null, "used_credits": null,
                         "utilization": null, "currency": null }
}

So for the example above the weekly window is 4% used (equivalently 96% remaining). Do not default a missing utilization to 0 (that hides the real number); if a window has no numeric utilization, omit that window instead. For extra_usage, map used_credits/monthly_limit to spend/limit and only show it when is_enabled is true.

One axis, consistently. "Used" and "remaining" are the same number from opposite ends (remaining = 100 - used). Whatever you choose to present, the label, the number, and any progress/meter for a given window must all describe the same axis. A meter or number labeled "left"/"remaining" must carry the remaining value, not the used value (a 4%-used week is "96% left", and a "left" meter should read nearly full, not nearly empty). This is a correctness constraint only - it does not require a meter, a number, or any particular label or layout.

Map those fields into this normalized shape:

type ClaudeQuotaSnapshot = {
  source: "oauth" | "cli";
  accountEmail?: string;
  plan?: string;
  windows: Array<{
    id: "five_hour" | "seven_day" | "seven_day_sonnet" | "seven_day_opus" | "extra_usage";
    label: string;
    percentUsed?: number;        // canonical, percent USED (0-100); derive remaining as 100 - percentUsed
    resetText?: string;
    resetAt?: string;
    spentUsd?: number;
    limitUsd?: number;
  }>;
  refreshedAt: string;
  stale: boolean;
};

Field mapping guidance:

  • five_hour becomes the current session window.
  • seven_day becomes the weekly window and should be the primary fallback if five-hour data is absent.
  • seven_day_sonnet and seven_day_opus become model-specific weekly windows.
  • extra_usage becomes extra usage spend and limit if present.
  • Clamp percentages to the inclusive range 0..100.

Claude CLI Probe Details

Run privileged CLI work in claude-code-quota/server.ts behind window.babyMenu.capabilities.invoke. Do not expose Node APIs to the renderer.

Command strategy:

  • Check whether claude exists on PATH.
  • Start claude --allowed-tools "" in a controlled child process or PTY.
  • Send /usage.
  • Capture rendered output and strip ANSI escape sequences.
  • Send Enter retries only if the usage panel has not appeared after a short delay.
  • Terminate the process after the probe.
  • Use a hard timeout of 15 seconds for the first implementation.

Parser expectations:

  • Find sections near text like Current session and Current week.
  • Extract either percent used or percent left.
  • If percent left is parsed, compute percentUsed = 100 - percentLeft.
  • Extract nearby reset text such as resets in 3h or resets at 5:00 PM.
  • Optionally parse Account: and Org: lines.
  • Surface authentication, token expired, or CLI update prompts as user-visible errors.

Implementation Contract

All data acquisition lives in claude-code-quota/server.ts: token reads, the CLI probe, network calls, timeouts, and parsing. Expose it as a getQuota server action invoked from the renderer with window.babyMenu.capabilities.invoke("claude-code-quota", "getQuota", input). Do not add preload methods, per-widget IPC channels, core renderer widgets, or WidgetHost registration; Baby Menu discovers extension widgets automatically.

The data is safe to refresh roughly every 5 minutes; how and when the widget triggers a refresh is the widget's concern, not this recipe's.

Do not add test or documentation files for the extension. Verify by reasoning through the parser paths, the server action response shape, and the widget's rendered unavailable, stale, and live states.

Server action response shape:

type QuotaResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: string; sourceTried: string[] };

Error Handling

These are data outcomes the server action returns, not UI copy.

  • If no token or CLI is available, return an unavailable error (Claude quota unavailable). Do not return mock data.
  • If a request times out, return the previous successful snapshot marked stale: true when one exists.
  • If credentials are expired, return an error of Claude sign-in required rather than silently using a stale token.
  • Never log, echo, or return token or cookie values in errors or logs.
