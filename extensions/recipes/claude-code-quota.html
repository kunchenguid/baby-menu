Claude Code Quota Widget Recipe

Capability

Add a baby-menu widget that shows Claude Code usage limits in the menu popover.

The widget should prefer real local Claude credentials and CLI output, then fall back to clearly labeled mock data only when no usable local source is available.

This recipe is self-contained. Do not require external source code, websites, or implementation guides to complete it.

User-Facing Behavior

  • Show current session usage and weekly usage when available.
  • Show model-specific weekly usage for Sonnet and Opus when available.
  • Show reset time text for each available window.
  • Show account email or plan when available.
  • Show last refreshed time.
  • Show loading, success, stale, unavailable, and error states.
  • Refresh automatically every 5 minutes by default.
  • Expose a manual refresh button.

Recommended Data Source Order

PrioritySourceUse WhenExpected Data
1 Claude OAuth usage API A usable OAuth access token exists. Five-hour, seven-day, Sonnet weekly, Opus weekly, extra usage spend, plan hints.
2 Claude CLI /usage probe OAuth is unavailable but the claude CLI is installed and signed in. Current session percentage, current week percentage, reset text, account and org lines when present.
3 Claude web API with manual cookie The user explicitly provides a Claude sessionKey cookie later. Session, weekly, model-specific usage, extra usage spend, account email.
4 Mock provider No real source is configured or readable. Static sample values labeled Mock data.

OAuth Usage API Details

Credential locations to check from claude-code-quota/server.ts only:

  • ~/.claude/.credentials.json
  • Future app-local credential cache under Electron user data, not committed to the repo.

Look for an OAuth access token with scope that can call usage APIs. Tokens with only inference scope may fail.

Request:

GET https://api.anthropic.com/api/oauth/usage
Authorization: Bearer <access_token>
anthropic-beta: oauth-2025-04-20

Map response fields into this normalized shape:

type ClaudeQuotaSnapshot = {
  source: "oauth" | "cli" | "web" | "mock";
  accountEmail?: string;
  plan?: string;
  windows: Array<{
    id: "five_hour" | "seven_day" | "seven_day_sonnet" | "seven_day_opus" | "extra_usage";
    label: string;
    percentUsed?: number;
    percentRemaining?: number;
    resetText?: string;
    resetAt?: string;
    spentUsd?: number;
    limitUsd?: number;
  }>;
  refreshedAt: string;
  stale: boolean;
};

Field mapping guidance:

  • five_hour becomes the current session window.
  • seven_day becomes the weekly window and should be the primary fallback if five-hour data is absent.
  • seven_day_sonnet and seven_day_opus become model-specific weekly windows.
  • extra_usage becomes extra usage spend and limit if present.
  • Clamp percentages to the inclusive range 0..100.

Claude CLI Probe Details

Run privileged CLI work in claude-code-quota/server.ts behind window.babyMenu.capabilities.invoke. Do not expose Node APIs to the renderer.

Command strategy:

  • Check whether claude exists on PATH.
  • Start claude --allowed-tools "" in a controlled child process or PTY.
  • Send /usage.
  • Capture rendered output and strip ANSI escape sequences.
  • Send Enter retries only if the usage panel has not appeared after a short delay.
  • Terminate the process after the probe.
  • Use a hard timeout of 15 seconds for the first implementation.

Parser expectations:

  • Find sections near text like Current session and Current week.
  • Extract either percent used or percent left.
  • If percent left is parsed, compute percentUsed = 100 - percentLeft.
  • Extract nearby reset text such as resets in 3h or resets at 5:00 PM.
  • Optionally parse Account: and Org: lines.
  • Surface authentication, token expired, or CLI update prompts as user-visible errors.

Manual Cookie Web API Details

This is not required for the first implementation unless OAuth and CLI are insufficient.

If implemented, require explicit user-provided cookie text and keep it out of git.

Required cookie name: sessionKey, usually with value prefix sk-ant-.

API flow:

GET https://claude.ai/api/organizations
Cookie: sessionKey=<value>

GET https://claude.ai/api/organizations/{orgId}/usage
Cookie: sessionKey=<value>

GET https://claude.ai/api/organizations/{orgId}/overage_spend_limit
Cookie: sessionKey=<value>

GET https://claude.ai/api/account
Cookie: sessionKey=<value>

Implementation Contract

Create or edit these extension files:

  • claude-code-quota/server.ts for privileged token, CLI, network, timeout, and parser work.
  • claude-code-quota/widget.tsx for a RefreshableBabyMenuWidget, using @babymenu/ui.
  • The widget should call window.babyMenu.capabilities.invoke("claude-code-quota", "getQuota", input).
  • Put quota reload logic in the widget's exported refresh method and set refreshIntervalMs to 5 minutes; WidgetHost owns timer and manual refresh calls.
  • Do not add preload methods, per-widget IPC channels, core renderer widgets, or WidgetHost registration; Baby Menu discovers extension widgets automatically.

Add repo-level tests:

  • tests/claude-quota.test.ts for parser and fallback tests.

Server action response shape:

type QuotaResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: string; sourceTried: string[]; mock?: T };

Error Handling

  • If no token or CLI is available, show Claude quota unavailable and offer mock data labeled as mock.
  • If a request times out, show Refresh timed out and keep the previous successful value as stale.
  • If credentials are expired, show Claude sign-in required.
  • Never print token or cookie values in renderer errors, logs, or tests.

Acceptance Criteria

  • The widget displays current Claude quota or a clear unavailable state.
  • The widget displays source label: OAuth, CLI, Web, or Mock data.
  • The widget displays when it was last refreshed.
  • The widget refreshes on a timer.
  • The widget exposes a manual refresh action.
  • The widget shows stale previous values if a refresh fails after a prior success.
  • The widget shows a clear error state if quota cannot be read.
  • Tests cover parser success, parser missing data, timeout/error fallback, and mock fallback.
